# Umang Hospital HIMS — OPD Extraction Design

**Date:** 2026-08-29
**Status:** Approved (design), pending implementation plan
**Source:** `d:\Agentix Project\Gov-HIMS`
**Target:** `E:\Umang Hospital HIMS`

## Objective

Produce a standalone Next.js application containing only the modules needed to
run a complete OPD patient journey for Umang Hospital:

```
Landing → Registration (voice or form) → Reception → Nurse/Vitals
        → Doctor Consultation → OPD completion
```

Five staff-facing surfaces survive: Patient, Reception, Nurse, Doctor, Billing.
Everything else in the source system — 24 other portals — is removed.

## Decisions

These were settled with the project owner before design and are not open
questions. They are recorded here because each one materially shapes the scope.

| # | Decision | Consequence |
|---|---|---|
| 1 | Doctor **creates** prescriptions and lab/imaging orders; no fulfilment portals | Write-side slices of the pharmacy/lab/radiology stores survive; all fulfilment logic is removed |
| 2 | **Reuse the existing Supabase project** (same URL, anon key, service role key) | No new migrations; `supabase/migrations/` is copied verbatim; the two apps share one database |
| 3 | **Full Billing portal** is in scope | `/billing/*` ships complete: dashboard, patient ledger, packages, discounts, refunds |
| 4 | Keep the landing page (Umang-branded), bilingual **en + hi**, the **voice registration agent**, and the **in-portal AI copilots** | OpenAI + ElevenLabs dependencies and `next-intl` remain |
| 5 | Teleconsult is **cut on both sides** | `/doctor/online` and `/patient/teleconsult` both removed — a doctor-side teleconsult with no patient screen to join is a broken half-feature, and it is not part of the six-step journey |

### Accepted risk: shared database

Decision 2 means the delivered project is standalone *as a codebase* but not as a
system. Umang and Gov-HIMS will share one Postgres instance, one RLS policy set,
and one auth user pool. A schema change made for either app affects both, and
demo data is common to both.

This is the owner's explicit choice and the build proceeds on it. Two mitigations
are in scope:

- `supabase/migrations/` is copied **complete and unmodified** (all 61 files).
  These are the applied history of a live database; pruning them would make any
  future `supabase db push` compute a diff against a history that never happened.
- The README states the shared-database constraint plainly, so it cannot be
  forgotten later.

A consolidated OPD-only migration set, for pointing at a fresh Supabase project,
is explicitly **out of scope** for this build and noted as the natural follow-up.

### The barrel problem

Three barrel files re-export across the entire system. Under a naive reachability
walk they make almost everything look reachable, because a single kept route
transitively pulls the whole application through them:

| Barrel | Effect |
|---|---|
| `src/components/StoreHydrator.tsx` → `src/lib/seed-legacy-stores.ts` | Mounted in the **root layout**; hydrates ~55 stores including CSSD, BMW, mortuary, dietary, blood bank, ambulance, vendor, narcotics, lab QC, housekeeping, HRMS, statutory, quality |
| `src/lib/api/index.ts` | `export *` across all 49 `lib/api/*` modules |
| `messages/{en,hi}/index.ts` | Imports all 46 locale namespaces (auto-generated by `scripts/i18n-barrel.mjs`) |

**This is the central technical risk of the extraction.** Deleting out-of-scope
code without first cutting these barrels produces a build that either fails on
missing imports or silently retains the entire system.

**Therefore pruning is iterative, not single-pass:**

```
1. Delete out-of-scope routes (per manifest)
2. Hand-prune the three barrels to in-scope entries only
3. Re-run reachability
4. Delete newly-unreachable files
5. Repeat 3–4 until the dead set is empty (fixpoint)
6. tsc --noEmit && next build && vitest run
```

Steps 3–5 are mechanical, which is what gives a subtractive extraction the same
"no dead code" guarantee an additive rebuild would have — without hand-tracing
171 unique import specifiers.

## Approach: subtractive clone

Mirror the repo to the target, then delete, rewire, and verify.

**Rejected — additive scaffold.** A fresh `create-next-app` with files copied in
along the import graph guarantees zero dead code, but the landing page, AppShell,
design tokens, and i18n layer are cross-cutting enough that most of the shared
layer gets copied anyway, after days of a half-broken shell.

**Rejected — monorepo with a shared package.** Contradicts the standalone
requirement and couples the two projects permanently.

The subtractive clone reaches a booting application on day one, and the
reachability fixpoint above recovers the additive approach's safety property.

## Order boundary

Decision 1 draws a line through three stores. The doctor's consultation keeps its
prescription pad and its lab/imaging order entry; nothing downstream of "ordered"
survives.

| Store | Retained | Removed |
|---|---|---|
| `usePharmacyStore` | Create prescription, read status | Dispensing, counselling, stock decrement, narcotics register |
| `useLabOrdersStore` | Create lab order, read status | Specimen collection, bench, result entry, verification, QC, reflex |
| `useRadiologyStudiesStore` | Create imaging order, read status | Scheduling, arrival, acquisition, reading, reporting, verification, distribution |

Patient and Reception views render these as `ordered`. No workflow advances them,
because the portals that would advance them are gone. Companion modules
(`lib/labCatalog.ts`, `lib/radiologyCatalog.ts`, `lib/reflexRules.ts`,
`lib/drugSafety.ts`) are retained only where the order-creation path reads them;
`lib/labReport.ts` and `lib/radiologyReport.ts` are report-rendering and are cut.

## Roles and authorisation

`src/types/roles.ts` shrinks from 29 roles to 6:

```ts
export const ALL_ROLES = [
  'doctor', 'nurse', 'reception', 'billing', 'admin', 'patient',
] as const
```

`admin` is retained **only** as the account type used to run seeds and ops
scripts against the shared Supabase project. **No `/admin/*` route ships**, and
`admin` appears in no nav table or portal card — it is a database role, not a
portal. It is kept rather than dropped because decision 2 shares the database
with Gov-HIMS, whose `profiles.role` column and RLS policies already recognise
`admin`; removing it from the enum would desynchronise the app's type from the
live schema.

`RoleGuard` and `AppShell` are unchanged in mechanism; their role tables are
reduced. `src/lib/permissions.ts` is **unreachable in the source system** and is
deleted rather than carried across.

## Dead code confirmed in source

Removed without replacement, and worth surfacing to the owner:

- **`src/rules-engine/` (all 7 modules)** — `allergy-block`, `drug-interactions`,
  `dosage-bounds`, `critical-values`, `triage-thresholds`, `billing-math`,
  `ot-gate`. Referenced from exactly one file, `components/lab/LabAnomalyPanel.tsx`,
  which is out of scope. **These clinical safety rules are not wired into the
  doctor's consultation in the source system.** They are not carried across.
  Wiring allergy and drug-interaction checking into the Umang prescription pad is
  a genuine clinical-safety improvement and is recorded as recommended follow-up
  work, explicitly outside this extraction's scope.
- `src/ai-services/index.ts` — barrel with no importers.
- `src/lib/permissions.ts`, `src/services/notification-dispatcher.ts`,
  `src/types/index.ts`, `src/data/cooKpis.ts` — unreachable.

## Verification

The journey is the acceptance criterion. All six steps must pass against the live
Supabase project:

1. Landing loads; portal launcher shows exactly five portals.
2. Registration completes by **form** — patient row created, UHID issued.
3. Registration completes by **voice agent** — same outcome via `/api/intake/turn`
   and `/api/voice/tts`.
4. Reception sees the new patient in the OPD queue and issues a token.
5. Nurse records vitals against that visit; they persist and appear on the
   doctor's screen.
6. Doctor opens the consultation, records diagnosis and notes, writes a
   prescription and a lab order, completes the visit.
7. Patient portal reflects visit, vitals, prescription, orders and bill.
8. Billing raises and settles the OPD consultation fee.

Gates, all of which must be clean:

- `npx tsc --noEmit`
- `npm run build`
- `npm run lint`
- `npm run test` (vitest; out-of-scope suites deleted with their modules)
- Reachability sweep reports an empty dead set
- No route outside the manifest resolves; no nav entry 404s

## Out of scope

- Consolidated OPD-only migration set / separate Supabase project
- Wiring `rules-engine` clinical safety checks into the prescription pad
- Any new feature not present in the source system
- Deployment configuration beyond what the source repo carries
